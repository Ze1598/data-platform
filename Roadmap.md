# Data Platform: Roadmap (current state + future work)

Architecture and design live in [README.md](README.md) — that's the permanent reference. This file tracks current state and what's not yet built; it and `Progress.md`/`Backlog.md`/`Learnings.md` are working documents for this project's build-out, not meant to outlive it. Completed-phase detail intentionally isn't duplicated here — see `Progress.md`, now an index into `Progress/`.

## Current state (as of 2026-07-27)

All numbered build-order phases (1–11, 13–15) are complete and live-verified — see `Progress.md`'s index for phase-by-phase detail. Phase 12 was removed from the roadmap. Nothing has a "next" designation right now — see `Backlog.md` for genuinely open, unscheduled items to pull from, and "Future work" below for larger, not-yet-scoped directions.

**Azure portability** is a deliberate design intention behind this project (see README.md's "Storage" bullet) — real ADLS Gen2 isn't a phase on this build order, and isn't something to implement here. Noted for context only.

## Future work (not on the numbered build order)

Genuinely future-facing directions, deliberately not treated as numbered phases — no committed design, scope, or sequencing yet. See `Backlog.md` for smaller, more concretely-scoped deferred items instead.

- **Front-end data visualization module** — deprioritized (2026-07-14), not built. Users would connect to a serve-layer view/table, pick a chart type/axes/legend, and the app renders via Plotly Express. Open decisions, not yet made: connectivity (ADBC vs. the plain `trino` client — the Trino ADBC driver isn't pip-installable, needs a separate binary install step, in tension with this project's all-`uv` tooling) and chart-config persistence (ephemeral per-session vs. saveable, which would need a new metadata table).
- **Unified security model, Azure Entra-integrable** — one security model defined once and applied platform-wide (frontend, metadata Postgres, Trino/Polaris, Kubernetes), rather than each subsystem managing its own access control independently. Proposed shape: the frontend centralizes role assignment, sourced from consumer user identities in Azure Entra; that role-assignment management generates role definitions, which in turn generate RBAC roles, security groups, and group assignments via infrastructure as code (see the IaC item below). Not scoped — open questions include how Entra identities map into this platform's own metadata schema, whether role definitions are platform-wide or per-module, how changes propagate, and how this interacts with Trino/Polaris's own native authorization versus Kubernetes RBAC versus the frontend's own access control.
- **Infrastructure as Code** — Terraform vs. Bicep not yet decided. Today's infrastructure (kind cluster, Kubernetes manifests, Helm installs) is entirely bash/kubectl/helm/`just`-recipe-driven, not IaC-managed. A real Azure deployment (the portability goal noted above) would need this; it's also the natural implementation vehicle for the security model item above (RBAC roles/security groups/group assignments as code).
- **Spark as a full alternative engine, staging/model layers included** — today, `data_feed.processing_engine` already lets a feed opt into Spark instead of Polars, but only for the raw→clean transform (Phase 6 above). This would extend that choice into staging/model, where dbt is currently the only option (`dbt-trino` has no Python model execution backend — a day-one architectural decision, not a gap) — Spark and Polars both becoming viable alternatives to hand-written dbt SQL for staging/modeling logic. A bigger structural change than the existing raw/clean opt-in: a new code path parallel to dbt entirely, not an extra dbt materialization option. Related to `Backlog.md`'s "Non-dbt staging engine (PyIceberg) for complex staging logic" entry, which already investigated a narrower version of this same problem (PyIceberg upsert only, not general Spark/Polars staging) — worth reading together, not duplicating.
- **Dependency-driven model build pipeline for `lakehouse_models`** — today, a `batch_group`-triggered `master_pipeline` run tiers feed extraction by `batch_feed_hierarchy` (built and live-verified, see `Progress/2026-07-25-batch-group-feed-tiering.md` — that mechanism is complete, not part of this item), *then* still runs every domain's entire staging+model dbt build as one job, *then* serving, regardless of which specific feeds each model actually needs. `lakehouse_models.batch_hierarchy` is inert metadata with no Dagster consumer. Proposed: launch a model's own staging+model build the moment its `depends_on_feeds` are satisfied — checked after each feed tier completes, not after the whole extraction phase — so a model whose feeds are all early-tier never waits on unrelated late-tier feeds, concurrently with later feed tiers still extracting for *other* models. Scoped to `orchestration_kind="batch_group"` runs that feed real hand-modeled `lakehouse_models` rows (ODS-producing batch groups and `model_schema`-triggered runs keep today's behavior unchanged — this mechanism doesn't apply to either). Not scheduled, no committed design yet:
  - **Ordering among ready models**: dims before facts (`table_type`, a baseline rule), then `batch_hierarchy` tier within each `table_type` — same tier-blocks-next-tier/siblings-independent rule as feed tiering.
  - **Failure semantics**: a failure only blocks what actually depends on it — unrelated branches run to completion; `master_pipeline`'s own final status still reports failure if anything failed anywhere, without cutting short unrelated in-flight work.
  - **Architecture**: one interleaved loop inside `master_pipeline`'s existing single op — not a separate "child pipeline" job per model. A feed shared by multiple models still only gets extracted once per run for free (there's exactly one global launch per feed), so no cross-run coordination/dedup mechanism is needed. The parallel launch/wait helper this needs already exists (`dagster_launch.launch_many_and_wait()`, built for feed tiering, directly reusable here). Still needed: new per-model `MODEL_BUILD_JOBS`/`MODEL_SERVE_JOBS` (`AssetSelection.assets(AssetKey(model)).upstream()`) added alongside — not replacing — today's whole-domain `MODELING_JOBS`/`SERVING_JOBS`.
  - **Operational gaps to resolve as part of this work**: nothing today caps *total* concurrent pods, only same-feed concurrency (the per-feed pool's `default_limit: 1`) — this design increases how many independent pods can be in flight at once, and needs a real ceiling. `dagster-webserver`/`dagster-daemon` are both hard-capped at 1 replica and become a real bottleneck for many concurrent job launches/status polls at this fan-out. Per-pod startup overhead (scheduling, image pull, container/interpreter init) versus small actual model-build work size is a real tradeoff of this fine-grained approach, not free parallelism. No connection-limit tuning exists today for Postgres/Trino/Polaris/MinIO against a higher concurrent-pod count. This project's local `kind` cluster is also a hard, fixed-size single-node ceiling (one Docker container, fixed CPU/memory) — genuinely cannot exercise "hundreds of concurrent pods" at all locally; real load behavior can only be validated against a real multi-node deployment, tying this directly to the Infrastructure as Code / node-autoscaling item above.
