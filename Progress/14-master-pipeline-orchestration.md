# Phase 14 — Master pipeline orchestration (in-cluster, real job-per-stage isolation)

**Status as of 2026-07-16: fully built and live-verified end to end.** Supersedes the earlier `FEED_JOBS`/`DOMAIN_JOBS`/`pipeline_init_<feed>`/`k8s_job_executor` structure entirely — see `README.md`'s "Master Pipeline Architecture" for the full design record (arrived at via direct back-and-forth design discussion) and `Learnings.md` for durable technical lessons; this section is the build/verification record only.

**Metadata schema**: `data_processing_runs` redesigned — `master_dagster_run_id` is now the row's primary identifying key (created once by `master_pipeline`'s own op, shared across every feed/domain row that run touches); `extraction_dagster_run_id`/`transformation_dagster_run_id`/`serving_dagster_run_id` store each child job's own separate run id. The `landing_*` column group is dropped entirely (folded into `raw_*` — "landing" was never a real pipeline-stage concept). `pipeline_steps` shrinks from 4 rows to 3 (extraction/transformation/serving).

**Job structure**: `scripts/generate_dagster_pipeline.py` now generates `EXTRACTION_JOBS[feed]` (raw+clean bundled as one job/pod — no separate validation job), `MODELING_JOBS[domain]`/`SERVING_JOBS[domain]` (selected by the exact `AssetsDefinition` object each domain factory returns, not a group-based selection), and exactly one `master_pipeline` job (`orchestration_kind`/`orchestration_value` op config) that resolves feeds/domains live from Postgres and launches child jobs via a new shared helper, `dagster_launch.launch_and_wait()` (submits via `DagsterGraphQLClient`, polls `get_run_status`, raises `dagster.Failure` on anything but `SUCCESS` — this is what makes a child failure stop the master pipeline). `k8s_job_executor` is dropped entirely, not fixed — once each stage is its own top-level job/pod, it would only add unwanted further nesting. New `raw_storage.py` makes the raw→clean handoff genuinely storage-based (`clean_<feed>` reads `raw_<feed>`'s durable parquet file back from disk via a `deps=` order-only dependency) — applied even within one job/pod, per direct instruction that this principle isn't just a cross-pod workaround.

**In-cluster Dagster deployment (`orchestration/k8s/`, new)**: real `Deployment`+`Service` for `dagster-code-server` (gRPC user-code server, `dagster api grpc`), `dagster-webserver`, and `dagster-daemon` (the piece that actually calls `K8sRunLauncher.launch_run()`, hence `load_incluster_config: true` + a new RBAC `Role`/`RoleBinding` for the `orchestration` namespace's `default` ServiceAccount). `orchestration/module.just`'s `start`/`kill` no longer touch a local `dagster dev` process at all — everything runs in-cluster, reachable at `localhost:3000` via a NodePort (kept unchanged for host tooling, same pattern as Postgres/Trino).

**Real bugs found and fixed during this build, all confirmed live (full write-ups in `Learnings.md`)**:
1. `financial_transactions_sensor` fired its feed's job directly, bypassing the master pipeline entirely — would have crashed every sensor-triggered run, since only `master_pipeline` creates the `data_processing_runs` row a child job now expects to already exist.
2. A stale `validation_dagster_run_id` column reference survived in `seed_metadata_db.py`'s `metadata_runs` query, from an earlier session's incomplete fix — crashed `metadata_runs`' own extraction live.
3. `clean_<feed>` declared its order-only dependency on `raw_<feed>` as a typed function parameter rather than `deps=` — crashed every single run with a missing-argument error, since Dagster's IO manager treats an upstream `Output(None)` as nothing-to-load rather than passing `None` through.
4. Mounting a ConfigMap directly as `DAGSTER_HOME` crash-loops the webserver/daemon (`OSError: Read-only file system`) — Dagster's telemetry/NUX subsystems write into `DAGSTER_HOME` at startup regardless of config; fixed via a writable `emptyDir` + an init container that copies the ConfigMap's files in first.
5. `jobs/status` needed its own explicit RBAC grant, separate from `jobs` itself — a 403 that only surfaced once the daemon's `MonitoringDaemon` actually ran in-cluster.
6. Rebuilding the image doesn't restart an already-running `dagster-code-server` pod (same image tag, no spec diff) — a structural code fix could silently not take effect; fixed by unconditionally `kubectl rollout restart`-ing it in `start`.
7. A stale local `dagster dev` process (over an hour old, predating this session's move to in-cluster Dagster) kept colliding with the new in-cluster daemon over heartbeat ownership in the shared `dagster_db` — only found because a `pgrep -f` pattern using `\|` alternation silently no-ops on macOS's BSD `pgrep` (unlike GNU `pgrep`/`grep`), producing a false "already dead" reading earlier in the same investigation.

**Verified live**: `just orchestration::verify-pipeline` (reworked to launch 3 real `master_pipeline` invocations — `model_schema=sales`, `model_schema=metadata`, `batch_group=police_crimes`, the minimum set covering every feed/domain exactly once, replacing the old single `__ASSET_JOB` launch which bypassed the master pipeline entirely) produced 5/5 successful feed-run rows + 3/3 successful domain model-run rows, plus confirmed durable raw files for `customers`/`sales`. `just orchestration::verify-schedule` (reworked the same way) and the full pytest suite (11/11) also green. A final full nuke-and-rebuild `just smoketest` was run afterward as the authoritative regression check: exit 0, 49/49 dbt tests, 11/11 + 5/5 + 6/6 pytest suites, no manual intervention needed.

**Metadata-driven per-domain Docker images (2026-07-17) — built and live-verified.** `MODELING_JOBS[domain]`/`SERVING_JOBS[domain]` are tagged with `dagster-k8s/config`'s `container_config.image`, overriding the shared `data-platform-orchestration` image with that domain's own `data-platform-domain-<domain>` image (confirmed against the installed `dagster_k8s` source that a per-job tag wins over the launcher's static config — no separate gRPC code-location per domain needed). `pipeline_generated.py`'s domain-construction loop now gates on `target/manifest.json` actually existing, not just `dbt_project.yml`, so a narrower per-domain image (missing every other domain's manifest) can still import successfully — every downstream dict (`TRANSFORMATION_ASSETS`/`SERVING_ASSETS`/`MODELING_JOBS`/`SERVING_JOBS`) only iterates domains actually present. `orchestration/Dockerfile` takes an optional `DOMAIN` build arg (unset = the full shared image, unchanged); new `orchestration/module.just::build-domain-images` builds+loads one image per domain discovered on disk, wired into `start`. Verified live via a full nuke-and-rebuild smoketest plus direct `kubectl get pods -o json` inspection: every `*_modeling_job`/`*_serving_job` pod ran from its own domain's image; every `extraction_*_job`/`master_pipeline` pod stayed on the shared image. Full detail in `Learnings.md`.

**Streamlit in-cluster Deployment (2026-07-17) — built and live-verified.** `frontend/k8s/` (new — didn't exist at all before, not even an empty placeholder) has the same `Deployment`+`Service` (NodePort, `localhost:8501` preserved) shape as Dagster's webserver. `frontend/Dockerfile` uses `uv sync --frozen --package frontend` (not `--all-packages`) — confirmed frontend has zero cross-workspace-package dependencies, and confirmed live via `uv sync --package frontend --dry-run` that `[tool.uv] package = false` in its own `pyproject.toml` doesn't prevent it being a valid scoped-sync target, it just means "don't build an importable wheel." `frontend/module.just`'s `start`/`kill` no longer touch a local `nohup streamlit run app.py` process.

**Sensor-triggered path test coverage (2026-07-17) — built and live-verified, two tiers.** `tests/test_sensors.py` (new) exercises `financial_transactions_sensor`'s evaluation logic directly via `build_sensor_context` (mirrors `test_schedules.py`'s pattern) — fast, no daemon, no live cluster. `verify_sensor_trigger.py` + `orchestration/module.just::verify-sensor` (new, wired into the root `Justfile`'s `smoketest` sequence) is the real end-to-end tier: starts the sensor for real (`DefaultSensorStatus.STOPPED` by default), drops a genuine CSV, waits for the actual daemon sensor-tick to detect it and launch `master_pipeline`, waits for that run to succeed, then always stops the sensor again afterward. `DagsterGraphQLClient` has no built-in sensor start/stop/run-listing methods — used its own `_execute()` directly with mutation/query shapes confirmed against the installed `dagster_graphql` schema source. Two real bugs found live while building this script (both in the script itself, not the platform): a genuinely empty test CSV crashes `CSVConnector.fetch()` (fixed: header-only CSV instead); and the sensor's cursor is real state persisted in `dagster_db`, independent of any one test run — a fixed test filename gets treated as "already seen" on a second run, and an earlier attempt's artificial far-future filename permanently blinded the sensor to every real future file until manually reset via `setSensorCursor`. Full write-up in `Learnings.md`. **Confirmed via a genuinely clean full nuke-and-rebuild `just smoketest`**: `verify-sensor` ran as part of the same sequence as `verify-pipeline`/`verify-schedule` (not standalone) from a fresh cluster for the first time — exit 0, 14/14 orchestration + 5/5 frontend + 6/6 integration pytest + 49/49 dbt tests all green together.

**`storage_watermark` column — pinning each run's raw read path (2026-07-17) — built and live-verified.** Added `data_processing_runs.storage_watermark` (text, nullable) — a `YYYY/MM/DD/HH/MM/SS` path generated once, at run-creation time, by `record_run_started()` (idempotent: `_ensure_run`'s `ON CONFLICT` branch never overwrites it, so a retried call reuses the same watermark). `raw_storage.py`'s `raw_snapshot_path`/`write_raw_snapshot`/`read_raw_snapshot` now key the raw parquet path by this watermark (`raw/<feed>/<storage_watermark>/<feed>.parquet`) instead of the extraction job's own `context.run_id`. Both the raw-writing and clean-reading steps read the value back from their own `log_data_feed_stage(...)` call — `_find_run()` now returns `storage_watermark` alongside `run_id` in the same `UPDATE ... RETURNING` round trip (no extra query), exposed as `IngestionStepLog.storage_watermark`. Updated: the DDL, `postgres_metadata_resource.py`, `raw_storage.py`, the hand-written `customers`/`sales` assets, and both of `scripts/generate_dagster_pipeline.py`'s connector-feed templates (covers `financial_transactions`/`metadata_runs`/`police_crimes`). One real bug found live during verification: `orchestration/module.just`'s `verify-pipeline` recipe independently reconstructed the expected raw file path itself (via `extraction_dagster_run_id` and the old `run_id=<id>` convention) rather than reading `storage_watermark` — missed during implementation since it lives in a `just` recipe, not any of the Python modules the raw/clean path logic itself lives in; fixed to read `storage_watermark` and build the new path shape. Confirmed via a full nuke-and-rebuild `just smoketest`: 5/5 feed-run + 3/3 domain model-run rows successful, durable raw files confirmed for `customers`/`sales` at the new path, schedule-triggered and sensor-triggered runs both succeeded, 49/49 dbt tests, 14/14 orchestration + 5/5 frontend + 6/6 integration pytest all green. A separately-raised idea from the same audit — a dedicated `archive` layer with a wipe-from-`landing`-on-success lifecycle — was reconsidered and closed as unneeded: `raw` already serves as the durable per-run record, and the operational safeguard (don't touch landing data while a run could still need to reprocess it) is a discipline rule, not a mechanism to build. See `Backlog.md` and `README.md`'s "Layer Model"/"Incremental Loading & Watermarks" sections.

**`data_feed.extraction_config` design correction, plus a generic connector default (2026-07-18) — built and live-verified.** Found while writing `Walkthrough_Metadata_Ingestion.md`: `metadata_runs`'s seeded `extraction_config` embedded a 3-table `LEFT JOIN` (feed/model friendly names and attributes) directly in the extraction query — real transformation logic running before `raw`, contradicting the platform's own "raw is a verbatim copy, not a transformation" contract (`README.md`, "Layer Model"). Root cause: `PostgresConnector` had no default behavior at all — `query` was a mandatory constructor argument, so every `postgres`-kind feed was forced to hand-write a full query even for a plain single-table pull. Fixed properly, not worked around: `PostgresConnector.__init__`'s `query` is now optional, defaulting to a generated `SELECT * FROM <table_name>` (`table_name` itself defaulting to `data_feed.source_object_name`) — `scripts/generate_dagster_pipeline.py`'s postgres connector-build template updated to match, preserving the explicit-query escape hatch for a feed that genuinely wants one. `metadata_runs` itself now uses the new default (`extraction_config` empty, no query at all); its `dbt/domains/metadata/` staging/fact models simplified to match — the two role-playing dimensions (`metadata_dim_feed`/`metadata_dim_model`) are retired entirely (`data_feed_id`/`model_key` carry through `fct_metadata_runs` as plain attributes instead, still expressing the source's real one-or-the-other-null shape without a dimensional join). `metadata/DataModel.md`'s `extraction_config` row rewritten to document the actual design: empty/default for a plain table source, reserved for genuine per-connector extras (REST pagination, CSV encoding/delimiter), with a fully custom query as a deliberate, clearly-scoped escape hatch. One real bug found live during verification, generic to the fix, not specific to this one feed: psycopg returns a native Postgres `uuid` column as a `uuid.UUID` object, which Polars can't infer a concrete dtype for under a plain `SELECT *` (crashed schema inference on `metadata_runs.run_id`) — fixed in `PostgresConnector.fetch()` itself, stringifying any `uuid.UUID` value in any row/column generically, not just for this feed's own columns. Also surfaced (and fixed, confirmed a test-design gap, not a pipeline bug): `tests/integration/test_utc_consistency.py`'s staging-timezone test assumed every `schema_registry`-discovered timestamp column also appears in `staging.<feed>` — true by coincidence for every prior feed, false for `metadata_runs` now that its `clean` schema (auto-discovered from a full-table `select *`) is genuinely wider than what its hand-curated staging model selects; narrowed to only check timestamp columns staging actually carries through. Confirmed via a full nuke-and-rebuild `just smoketest`: all 3 `master_pipeline` invocations succeeded (including `model_schema=metadata`), 49/49 dbt tests, 14/14 orchestration + 5/5 frontend + 6/6 integration pytest all green.
