# Phase 11 — Real-time / streaming ingestion

- [x] Design the write path: topic/table layout, exactly-once vs. at-least-once landing semantics, whether streaming tables ever fold into `staging` proper vs. staying serve-only real-time views
- [x] New module (`streaming/`) — Kafka (KRaft, single broker) as the ingest broker, Flink (via the Flink Kubernetes Operator) landing topics as an append-only Iceberg table in the same Polaris-cataloged warehouse
- [x] **Verify**: a real-time stream table joins straight into the already-persisted `model` layer via ordinary Trino SQL with no new query-engine integration — `serve.sales_streaming_sales_events` (a hand-authored dbt view) joins `streaming.sales_events` to `model.sales_dim_branch`, confirmed live: every branch value resolved a real city, not a null

**Status**: first-pass slice built and live-verified (2026-07-18) — one streaming table, one joined serve view, deliberately bounded per the design decisions below. Not the full generalized "onboard any new stream with zero code" system a batch feed gets; that's a real follow-up, not part of this pass (see Backlog.md).

Notes / deviations:

- **Scope, decided directly with the user before implementation**: Kafka + **Flink** (not Kafka Connect) for real stream-processing headroom later; **no fold-in to `staging`/`model`** — stays a serve-only real-time view for now; **no new Postgres metadata table** and no `data_feed`/`lakehouse_models` changes — every existing metadata table/codegen script assumes a discrete, bounded, watermarked run, which streaming isn't, and building a speculative metadata-driven onboarding system before a second real stream exists would be premature generalization. This first pass is pure static config (k8s manifests + one SQL script + one dbt view), directly analogous to how Phase 3 proved Trino+Polaris+MinIO by hand before Phase 5 built any metadata automation around it.
- **PyFlink was tried first and abandoned** — chosen initially to avoid writing any Java, it turned out to force every image in this module onto a `--platform linux/amd64` cross-architecture build (PyFlink's `pemja` dependency has no Linux/arm64 wheels), which then failed to load into this project's arm64 kind cluster via the normal `kind load docker-image` path (the image lands in containerd's content store but isn't surfaced to the CRI image service kubelet actually queries — a real, not previously encountered, class of failure on this cluster). Switched to a vendored Java driver (`org.apache.flink.examples.SqlRunner`, copied verbatim from `apache/flink-kubernetes-operator`'s own reference example) after directly comparing the real maintenance surface of both paths: the Java involved is ~140 lines, generic, and needs zero modification per new streaming source (onboarding a new source is purely a new `.sql` file); PyFlink's "zero Java" didn't actually reduce per-source work (each source still needs its own bespoke Python driver) and came with the structural arm64 problem. Full investigation in Learnings.md.
- **Two real Iceberg/AWS gotchas found getting Flink to write into the warehouse at all**, both in Learnings.md: (1) `iceberg-flink-runtime`'s `FlinkCatalogFactory.clusterHadoopConf()` unconditionally needs `org.apache.hadoop.conf.Configuration` on the classpath even for a pure REST-catalog + S3FileIO setup that never touches HDFS — fixed with Hadoop's modern `hadoop-client-api`/`hadoop-client-runtime` (3.5.0) shaded jars, not the old `flink-shaded-hadoop-2-uber` (Hadoop 2.8.3, last published years ago) most tutorials cite. (2) The Flink TaskManager builds its own separate AWS S3 client for actual data writes that doesn't inherit the catalog's own `s3.*` properties — the same class of gotcha this repo already hit for Polaris's own server-side `S3FileIO` client — fixed the same way, explicit `AWS_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_ENDPOINT_URL_S3` env vars on the FlinkDeployment's pods.
- **A third real gotcha, in the SQL itself**: Flink SQL's `CAST(string AS TIMESTAMP(6))` fails *silently* (no exception anywhere, just a real Iceberg commit with `dataFilesCount=0`) on an ISO-8601 `'T'`-separated timestamp string — Python's default `datetime.isoformat()` output. The synthetic producer (`streaming/producer/`) emits the SQL-standard space-separated format instead (`strftime('%Y-%m-%d %H:%M:%S.%f')`). Full detail in Learnings.md.
- **New synthetic producer** (`streaming/producer/`, `confluent-kafka` client, new uv workspace member) — mirrors `customers`/`sales`' existing synthetic in-memory generators; branch/city/product_line vocabulary matches `sales_assets.py`'s real `_BRANCHES`/`_PRODUCT_LINES` exactly, so the streaming events' `branch` values genuinely match `sales_dim_branch`'s real rows for the join, not an unrelated fictional set. Runs as a genuine long-running `Deployment`, not a `Job` — the first in this repo, since every other custom compute here is bounded/run-to-completion.
- **Second exception to "one image per module"** (`README.md`'s Kubernetes Hosting Model table) — `streaming` owns a custom Flink image (Maven-built Java driver + downloaded connector JARs) and a custom producer image; `orchestration` was the only documented exception until now.
- **Cluster memory confirmed tight, not just theoretically**: the full existing stack (Postgres, Polaris, MinIO, Trino, 3 Dagster deployments, Streamlit) plus the entire `streaming` module running simultaneously measured at ~87% of Docker Desktop's 7.65GB VM budget. It fits, with limited headroom — noted directly in `streaming/flink/module.just`.
- **Verified live**, not just built: `just kill streaming` → `just start streaming` end-to-end through the real wired `just` recipes (not manual `kubectl`/`docker` commands) — Kafka round-trip, Flink job reaching `RUNNING`, Iceberg row count growing over consecutive checks, `dbt run` building the serve view, real branch/city join resolution, and `check_model_feed_tags.py` confirmed silently ignoring the new `lakehouse_models`-less view as expected. Full existing test suite (49 dbt tests, orchestration/frontend/processing/tests-integration pytest) re-run afterward, all green — no regression.

## Phase 11 (continued) — Generalized streaming onboarding + demand-driven scaling (2026-07-18)

**Status**: the "onboard any new stream with zero code" system deferred at the end of the first pass above is now built, and a second real streaming source (`inventory_events`) is live and growing independently alongside `sales_events`, proving genuine multi-source concurrency, not just a second hand-copy of the first slice.

**Metadata-driven streaming onboarding**:
- New `streaming_source` metadata table (friendly_name, topic_name, table_name, model_schema, event_timestamp_column, jobmanager_memory/taskmanager_memory/taskmanager_cpu/parallelism, autoscaler_enabled, is_active) — the streaming analog of `data_feed`.
- `schema_registry` generalized from feed-only to polymorphic (`controlling_object_id`/`controlling_object_type` in `('feed', 'streaming_source')`), mirroring `ingestion_triggers`' existing polymorphic pattern. `PostgresMetadataResource.update_schema_registry()`/`get_current_schema()`/`get_current_primary_key_columns()` took the new keyword params with defaults preserving every existing feed call site; `sync_schema_registry()`'s own signature stayed feed-specific by design.
- Two new codegen scripts, deliberately different postures matching `generate_model_scaffolds.py` vs. `generate_serve_views.py`'s existing split: `generate_streaming_ingestion.py` (100% generated, safe to wipe-and-regenerate — Flink SQL sink script + `FlinkDeployment` CR + Kafka topic-creation Job, from `streaming_source` + its current `schema_registry` entry) and `generate_streaming_serve_scaffolds.py` (write-if-missing — a bare `SELECT *` scaffold + source `.yml`, business-logic join left as a TODO the same way a fact's dimension join is).
- New Streamlit page (`5_Streaming_Sources.py`, renumbered from `4_Streaming_Sources.py` on 2026-07-27 once it collided with `4_Ingestion_Triggers.py`) for CRUD plus a live "Discover schema" action (`confluent_kafka.Consumer` samples real topic messages, `connectors.inference.infer_column_definitions` derives column types, writes a `schema_registry` version) — the same discovery-bootstraps-it pattern `data_feed` already uses, applied to streaming.
- **Confirmed, not assumed**: after any full nuke-and-rebuild, `schema_registry` is *always* empty for every `streaming_source` row — including ones that have run successfully before — since it's deliberately never seeded (same rule as `data_feed`). This means discovery has to be re-run by hand for every streaming source after every nuke before `generate_streaming_ingestion.py` will consider it "ready" to deploy; `just start`/`just smoketest` alone never bring up a `FlinkDeployment` on their own. Not a bug — a real, permanent operational consequence of this design, worth knowing going in.

**Batch/streaming dbt build-graph separation (a real bug found and fixed)**: running the full pipeline end-to-end for the first time since the generalization surfaced that `sales_modeling_job` — the ordinary batch transformation step, unrelated to streaming — failed with `TrinoUserError: TABLE_NOT_FOUND` building `serve.sales_events`/`serve.inventory_events`, because those streaming serve views were swept into the regular batch build graph (tagged `['sales', 'streaming']`/`['streaming']`, neither excluded by the existing `serving_layer` exclusion) and raced Flink's first Iceberg checkpoint. Fixed with a three-tier tagging scheme on every streaming serve view — a blanket `streaming` tag (excluded wholesale from `_build_transformation_assets_for_domain`'s dbt selector, `dbt_assets.py`'s new `_STREAMING_TAG`) plus `streaming_<model_schema>`/`streaming_<table_name>` for future per-domain/per-object selection, prefixed the same way `domain_group_name()` already prefixes with `domain_` to avoid colliding with a same-named feed's own per-feed tag (e.g. the `sales` domain vs. the `sales` feed). Batch and streaming are now genuinely independent build graphs — the only real coupling left is streaming serve views joining *out* to already-persisted model-layer tables, which are assumed to already exist (batch-first design intent, confirmed directly with the user).

**KEDA scale-to-zero for `orchestration` (webserver + code-server)**, triggered by this generalization work hitting a real memory ceiling onboarding the second stream: full comparison of KEDA/Knative/HPA/VPA/Cluster Autoscaler written into `Learnings.md`; KEDA core + Cron scaler adopted (CNCF Graduated, no beta components), scoped to webserver+code-server only (daemon stays always-on). A real bug surfaced proving this out for real: a plain `kubectl scale` doesn't stick against a Deployment a `ScaledObject` targets — KEDA's own HPA reconciles it back to the trigger's computed value (0, outside the Cron window) within ~15s, which is what the first live `verify-pipeline` run actually hit (a `ConnectionResetError`, not a readiness-probe race as first suspected). Fixed with KEDA's own `autoscaling.keda.sh/paused-replicas` annotation (`_wake-orchestration`/new `_sleep-orchestration`, the latter registered via `trap ... EXIT` so it always runs) — confirmed live in both directions: paused holds the Deployment (HPA disappears entirely while paused), unpaused hands control straight back to KEDA. Full detail in `Learnings.md`.

**Final proof, live**: `sales-events-sink` and `inventory-events-sink` both reached `RUNNING`/`STABLE` concurrently, each with its own JobManager + TaskManager pod running side by side (the exact memory-ceiling scenario that started this whole detour). Row counts confirmed independent (`sales_events` at 325 from its continuous producer, `inventory_events` growing 5 → 8 across two manual produce batches, exact match). Full `just smoketest` (nuke → rebuild → pipeline/schedule/sensor verification → full test suite) green throughout — 49 dbt tests, 14 Dagster tests, 5 frontend tests, 6 integration tests, no regression from the `schema_registry` polymorphic migration, the KEDA changes, or the tagging fix.

**Caveat on the above, corrected by the next entry**: this proof was live but manual (hand-run discovery/message production against a live cluster, not through any `just` recipe) and never actually rebuilt the streaming serve views via dbt after the tagging fix — the join logic itself (not just the raw Iceberg sink) was unverified post-fix. See below.

## Phase 11 (continued, part 2) — Isolated streaming test suite + full end-to-end validation (2026-07-18)

**Status**: `just smoketest` now validates streaming for real, automatically, as part of the platform's own standing regression-testing methodology — not a manual one-off proof. New module `streaming/testing/` (workspace member, own Dockerfile/image) + new `streaming-testing` mod (`just streaming-testing::test`, wired into `just smoketest` as its final step, skippable via `just smoketest skip_streaming=true`).

**Design goal, stated directly by the user**: streaming tests must be *isolated* — provable without requiring the batch pipeline (`master_pipeline`) to have run first — not full integration tests gated on batch. Solved with a small, explicitly hand-maintained dummy model-layer fixture (`run.py`'s `_MODEL_LAYER_FIXTURES` — today just `model.sales_dim_branch`, created via `CREATE TABLE IF NOT EXISTS` + populated only if empty, so a real batch-built table is never touched) and hand-maintained sample messages per known source (`_MESSAGE_FIXTURES`) — same "no metadata describes this, a human writes it once" posture already established for the serve-view joins themselves and for `generate_streaming_serve_scaffolds.py`'s scaffolds.

**Runs in-cluster as Kubernetes Jobs, not from the host** — Kafka's Service is ClusterIP-only (Learnings.md), so anything touching Kafka has to run in-cluster; Postgres/Trino are reached the same way (in-cluster DNS) for one consistent execution path. Jobs (delete-then-recreate, `backoffLimit: 0`), not `kubectl run --rm`, for reliable exit-code/log inspection.

**Three-stage verification, not just "does it deploy"**: `setup` (ensure fixtures, seed messages, run schema discovery for every undiscovered active source) → `verify-raw` (produce more messages, confirm each source's raw `iceberg.streaming.<table>` row count actually grows) → (host-side `dbt build --select tag:streaming`, using the tagging fix from part 1 above) → `verify-serve` (confirm each source's dbt serve view, `iceberg.serve.<table>`, returns real rows). Both raw and serve checks matter separately — a raw sink can grow correctly while its serve view is still broken (wrong join key/column), which is exactly the class of bug this closes the gap on.

**Two real bugs found and fixed building this, not just plumbing**:
- `discover_source()`'s `sample_size` default (20) didn't match `seed_source_messages()`'s own default message count (5) — every discovery run polled Kafka for up to ~200s per source waiting for messages that would never arrive, since only 5 were ever produced. Fixed by matching the defaults (5) and shortening the per-poll timeout.
- The hand-duplicated `schema_registry` write (`_write_schema_registry_version`, kept separate from `PostgresMetadataResource.update_schema_registry` since `streaming-testing` has no real dependency on the orchestration package) omitted the `version` column entirely (`NOT NULL`, computed as `max(version)+1`) and `effective_to` — failed live with `NotNullViolation` on the first real run. Fixed by copying the real INSERT verbatim instead of reconstructing it from memory — a direct lesson for any future duplicated-write-path code in this repo.

**Verified live, twice**: once as individually-run steps (confirmed the join itself resolves — `serve.sales_events` queried directly, zero null `city` values, real branch/city data flowing through the dummy fixture), then as the full composite `streaming-testing::test` recipe standalone, then as the actual final step of a genuine full `just smoketest` (nuke → rebuild → batch verify → full test suite → streaming tests) — all green, zero failures anywhere in the log. In that final full run, `model.sales_dim_branch` already had real batch-built rows by the time streaming tests ran (proving the fixture correctly detects and defers to real data, per its own non-destructive design) — the standalone runs earlier are what proved the true batch-independent case.

## Phase 11 (continued, part 4) — Streamlit "Trigger a Dagster run" feature (2026-07-19)

**Status**: new page `frontend/pages/6_Trigger_Pipeline.py` (renumbered from `5_Trigger_Pipeline.py` on 2026-07-27, see the numbering-collision fix below) — the first real UI path to launch `master_pipeline` on demand, closing the Backlog.md gap that blocked the cooperative-wake-up item. Lets a user pick `orchestration_kind` (`batch_group`/`model_schema`) and a real value (populated live from `data_feed.batch_group_friendly_name`/`lakehouse_models.model_schema`), submits via Dagster's GraphQL API, and shows a "Recent runs" table (`data_processing_runs`) so the user can watch the outcome without needing Dagit.

**Design decision**: calls the Dagster webserver's `/graphql` endpoint directly via `requests`, replicating `dagster_graphql.DagsterGraphQLClient`'s own two queries (repository-location resolution + `launchPipelineExecution`) verbatim rather than depending on the `dagster-graphql` package — that package pulls in the full `dagster` core as a transitive dependency, a large, deliberately-avoided addition to an otherwise-lightweight CRUD frontend for one GraphQL call. Both queries verified live against the real mutation/response shape before being written into the page (`__typename` confirmed as `LaunchRunSuccess` against this platform's actual installed `dagster-graphql` 1.13.12, not assumed from the client library's source).

**Explicitly out of scope at the time, by design, not an oversight**: no cooperative wake-up. If KEDA had scaled `orchestration` to zero, the page failed with a clear, explained `st.error` (verified live) rather than a raw stack trace or a silent hang. Waking orchestration automatically was kept as its own, separate, more involved backlog item — kept distinct per this project's own "prove one thing before building the next dependent one" pattern. **Built 2026-07-20** — see `Progress/2026-07-20-cooperative-wake-up.md` for the full build, including a real race condition found and fixed along the way.

**Three real bugs found — the first two only after the user directly pointed out this page had never actually been tested for real**, and correctly called out that the earlier "verified live from inside the real deployed pod" claim wasn't true testing (a `kubectl exec`-copied snippet of just the trigger function, never the page's own top-level code):
1. `fetch_table(engine, "data_feed")` crashed on load — silently relied on `fetch_table`'s `order_by="created_at"` default, but `data_feed` has no such column. Never caught because neither `curl` (returns 200 regardless — Streamlit serves a static shell over plain HTTP, the real script only runs over the browser's WebSocket connection) nor the hand-copied trigger-function snippet ever executed the page's actual top-level code.
2. Even after fixing (1) with `streamlit.testing.v1.AppTest` (Streamlit's own headless script-running harness — the real fix, see `Learnings.md`), the `batch_group` dropdown populated from `data_feed.batch_group` — a `uuid` column — instead of `batch_group_friendly_name`, the text `PostgresMetadataResource.get_batch_group_feeds()` actually matches against. Submitting a uuid returned `LaunchRunSuccess` every time (the mutation genuinely succeeds) but the launched run always failed inside Dagster with "No active feeds resolved" — caught only by extending the test suite to poll `data_processing_runs` for the *specific* submitted `run_id`'s outcome, not by accepting a success message or a "recent rows" spot-check (which had been silently satisfied by an unrelated `just smoketest` run's leftover rows).
3. Separately, a genuine redeploy mechanism bug (not specific to this page — see `Learnings.md`): `frontend/module.just`'s `start` never forced a pod restart, so a rebuilt image sat loaded-but-unserved while the already-running pod kept serving old file content indefinitely — meaning bug (1)'s fix had already been "deployed" twice without ever actually reaching the running pod, confirmed by `kubectl exec`-ing in and reading the file directly. Fixed by adding `kubectl rollout restart` (same fix `orchestration/module.just` already has for `dagster-code-server`, just never applied here or to `streaming/producer/module.just`, which had the identical bug).

**`frontend/tests/test_trigger_pipeline_page.py`** (new) is the actual, durable fix for all three — `AppTest.from_file(...)` runs the real page script headlessly; `test_trigger_button_batch_group_resolves_real_feeds`/`..._model_schema_resolves_real_feeds` extract the real `run_id` from the success message and poll for that exact run's `job_successful = true` row, not just "the mutation was accepted." Confirmed each test would have caught its bug: reverted the `order_by` fix locally and re-ran — same `DatabaseError` as the browser; reverted the `batch_group_friendly_name` fix and manually resubmitted a uuid — same `Failure: No active feeds resolved` Dagster-side. Final state: 5/5 tests passing against a freshly-redeployed pod (`deployment.apps/frontend restarted` confirmed in the apply output, not just `unchanged`), real feed names (not uuids) confirmed in `data_processing_runs` for both `orchestration_kind` values.
