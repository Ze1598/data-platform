Notes / deviations:

A full redesign of the metadata schema, driven entirely by a detailed table-by-table review (design captured in [metadata/DataModel.md](../metadata/DataModel.md), now the source of truth for this schema — `README.md`'s "Metadata Schema" section just points there instead of duplicating it).

- **`source_system`**: `user`/`secret` renamed to `connection_user`/`connection_secret` (`user` is a Postgres reserved word); new `base_location`.
- **`data_feed`**: `code` removed — `friendly_name` (renamed from `object_name`) is now the identity/idempotency key everywhere (seed script, asset `get_data_feed()` lookups, frontend selection). `name` dropped. New `source_object_name`, `source_pk` (renamed from `business_key_columns`), and `batch_group`/`batch_group_friendly_name`/`batch_feed_hierarchy` (batching concept, not yet consumed by a real scheduler — every feed still gets a singleton batch of its own name, enforced not-null since the platform is meant to track runs by batch, never by a bare feed). `incremental_column`/`incremental_column_type` collapsed into `watermark_column`. `staging_table_name`/`schedule_cron`/`landing_path_template`/`raw_path_template`/`updates_enabled`/`created_at`/`updated_at` all removed — path/naming conventions are pure code now, and staging's update-tracking behavior moved to a derived rule (see below).
- **`model_feed` → `lakehouse_models`**: `code`→`friendly_name`, `model_type`→`table_type`, `deletions_enabled`→`deletes_enabled`. New `model_schema`, `batch_hierarchy`, `load_type` (new lookup table: full/incremental_by_id/incremental_by_timestamp/incremental_by_custom_query). `staging_source_data_feed_id` + the `model_feed_source` bridge table both replaced by a single `depends_on_feeds` (comma-separated `data_feed.id`s) — staging itself still has no metadata row of its own, this is fact/dimension-only. `surrogate_key_column`/`created_at`/`updated_at` dropped.
- **New staging update-tracking rule**: since `data_feed.updates_enabled` is gone, a feed's staging table now tracks updates if *any* `lakehouse_models` row listing it in `depends_on_feeds` has `updates_enabled=true`, defaulting to `true` if no dependents exist. Implemented in `PostgresMetadataResource.get_updates_enabled_map()`. Consequence: `sales` reverts to update-tracking under the default rule unless its dependents say otherwise — both `dim_branch` and `fct_sales` are seeded `updates_enabled=false` to deliberately preserve the earlier-established "sales is immutable" behavior.
- **New `schedule` table** (polymorphic `controlling_object_id`/`controlling_object_type` in `feed`/`model`) — table-only at first, no codegen consumer yet. **Update**: now has a real consumer, see "Dynamic pipeline foundation" below.
- **`insert/update-split` mechanism unaffected** by the rename — `classify_changes()`/`trino__get_delete_insert_merge_sql` just consume whatever `updates_enabled` value they're handed.
- **Real bug found and fixed along the way, unrelated to the schema itself**: `raw_police_crimes` was flattening the API's nested JSON (a `clean`-layer responsibility) instead of being a verbatim, zero-transformation dump, and never actually wrote anything to `raw/` storage. Fixed: flattening moved into `clean_police_crimes`; `raw_police_crimes` now writes the untouched nested rows to `raw/police_crimes/run_id=<id>/crimes.parquet` (parquet specifically to survive the round-trip with nested struct columns intact). See Learnings.md, "A stub asset can silently violate a documented layer contract indefinitely" for the general lesson (second occurrence).
- **Every call site updated**: seed script (`friendly_name`-keyed idempotency, `depends_on_feeds` resolved via `string_agg` subquery), `PostgresMetadataResource` (`get_data_feed()`, merged `log_data_feed_stage()`/`log_data_model_stage()` onto `data_processing_runs` with a new `tracking_group` parameter, rewritten `get_updates_enabled_map()`), all 4 asset files, `dbt_assets.py`, both codegen scripts (`generate_serve_views.py` now tags a view with *every* feed in `depends_on_feeds`, not just one), all 3 frontend CRUD pages (`3_Model_Feeds.py` renamed to `3_Lakehouse_Models.py`, gained a multi-select `depends_on_feeds` picker and a batch-group picker with inline "create new batch" support), `orchestration/module.just`'s `verify-pipeline`, and a stale integration test (`test_utc_consistency.py` was still querying `data_feed.code`/`staging_table_name`).
- **Also discovered while wiring `verify-pipeline`**: a from-scratch cluster had never actually exercised `financial_transactions`' full pipeline before, because `clean_financial_transactions` silently no-ops on an empty `landing/` and nothing ever regenerated the landing CSVs this session's earlier data cleanup wiped. Fixed by adding `orchestration::seed-financial-landing` (runs `generate_financial_reports.py` once, only if `landing/financial_transactions/` is empty) to `orchestration::start`, so this can't silently recur.
- **Verified live, not just designed**: full `just smoketest` (nuke, rebuild, live `__ASSET_JOB` run, full test suite) green — 4/4 feed-run + 4/4 model-run rows in `data_processing_runs`, 44/44 dbt tests, every pytest suite — plus a direct CRUD round-trip (insert/update/delete) against `data_feed` and `lakehouse_models` using the exact same helper functions the Streamlit pages call, since no headless browser is available in this sandbox to click through the UI itself.

## Dynamic pipeline foundation, real schedules, multi-feed model

Asking to test `schedule` functionality surfaced that there was no dynamic, metadata-driven pipeline at all — every feed's jobs were hand-written Python, only 2 of 4 feeds even had a dedicated triggerable job, and `police_crimes_schedule`'s cron was a hardcoded constant. Full addendum plan in `.claude/plans/i-want-to-create-calm-manatee.md`; approved and implemented in full.

- **Every feed now gets a real, generated job** (`customers_job`/`sales_job`/`financial_transactions_job`/`police_crimes_job`), replacing the two hand-written ones and the `__ASSET_JOB`-only reliance for `customers`/`sales`. Driven by `group_name=<feed friendly_name>` on every asset (hand-written + dbt, via a new `DataPlatformDbtTranslator.get_group_name()` override) and a new build-time codegen script, `scripts/generate_dagster_pipeline.py` → `pipeline_generated.py` (same "structural decisions are codegen, never a live Postgres read at import time" rule as `generate_serve_views.py`).
- **`schedule` rows become real Dagster schedules**: a feed-type row → one generated `@schedule`; a model-type row → one generated schedule *per feed in that model's `depends_on_feeds`* (a schedule binds to exactly one job, and models have no standalone job). Each schedule's execution function re-checks `is_active` and looks up the target's current `batch_group_friendly_name` live at every tick (`PostgresMetadataResource.is_schedule_active()`) — structure is build-time, values are runtime, matching the user's stated preference.
- **New multi-feed test model**: `fct_daily_financial_activity` (row-grain `UNION ALL` of `stg_sales` + `stg_financial_transactions`, keyed by `(source_feed, source_id)`), `depends_on_feeds=[sales, financial_transactions]`. First lakehouse_models row depending on `financial_transactions` — flips `stg_financial_transactions` from the zero-dependents default (`updates_enabled=true`) to `false`, matching that staging model's own already-stated insert-only assumption (correction, not regression).
- **`customers`/`sales` raw semantics brought in line** with `financial_transactions`/`police_crimes` — `raw_customers`/`raw_sales` now write a durable parquet file to `raw/<feed>/run_id=<id>/`, no archive step (synthetic smoketest data, no retention need).
- **Real bugs found and fixed during implementation, not just design-time**:
  1. A dbt model tagged with two feed tags gets claimed by *two* separate `@dbt_assets` Python defs, which Dagster rejects as a duplicate AssetKey — hit for real on both the base model and the derived serve views (`generate_serve_views.py` was independently tagging with every `depends_on_feeds` member). First fix (deterministic alphabetically-first tag, agreed by two comments) was a real workaround, not a proper fix — **superseded** by adding `lakehouse_models.owning_feed_id` (real, required FK to `data_feed`, separate from `depends_on_feeds`): both the base model's tag and `generate_serve_views.py`'s generated tag now read this one column instead of independently guessing. Considered and rejected: collapsing to one `@dbt_assets` function for the whole dbt project (dagster-dbt's own recommended pattern here) — `@dbt_assets`' `pool=` has no per-model override, so collapsing would force every feed onto one global concurrency pool, a real regression. See `Learnings.md` for the full writeup, including the still-open gap (no automated check that a model's hand-written `tags=[...]` actually matches `owning_feed_id` — noted in `Backlog.md`).
  2. A `@schedule` function requesting a resource must declare it as a named parameter (`def _fn(context, postgres_metadata: ...)`), not pull it from `context.resources` — `ScheduleDefinition.__call__`'s resource-injection matches by parameter name, and passing `required_resource_keys=` as well is rejected outright ("cannot specify resource requirements in both").
  3. A GraphQL-submitted run only queues — the daemon creates the actual k8s Job a moment later, same asynchronous gap `verify-pipeline`'s job-name-diffing loop already existed for. `verify-schedule` needed the same appear-then-wait pattern, not a direct `kubectl wait`.
- **Verified live**: full `just smoketest` green (`verify-pipeline` 4/4+4/4 plus new durable-raw-file assertions, new `verify-schedule` recipe launching a real schedule-evaluated run end-to-end via `dagster_graphql.DagsterGraphQLClient`, 54/54 dbt tests including the new model, 5/5 orchestration tests including 4 new schedule tests, full pytest suite).
- **Explicit backlog note, not implemented**: CRUD for `schedule` rows in the frontend, per the existing `2_Data_Feeds.py`/`3_Lakehouse_Models.py` pattern.
