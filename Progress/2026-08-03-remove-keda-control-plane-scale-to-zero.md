# Remove KEDA scale-to-zero for the Dagster control plane (2026-08-03)

Investigated whether Backlog.md's "Cooperative wake-up's 60s grace period doesn't cover the host-CLI trigger path" entry was still a real, live issue or a stale/transient artifact from a prior session. Confirmed still live and unresolved by code inspection: `wake_sleep_sensor.py`'s `_WAKE_GRACE_PERIOD_SECONDS` was still `60`, no commit since the original 2026-07-20 fix had touched the wake/sleep mechanism, and `Progress/2026-07-27-frontend-apptest-coverage.md` records the same `ConnectionResetError` race being hit and retried around as recently as that date.

**Root-caused rather than assumed**: `orchestration::verify-pipeline` calls `_wake-orchestration` once, then runs three sequential `master_pipeline` invocations (`model_schema=sales`, `model_schema=metadata`, `batch_group=police_crimes`), each blocking until terminal. The wake-timestamp grace period is stamped only at that single initial wake and never refreshed before the 2nd/3rd launch. Since a single `master_pipeline` run takes minutes, by the time run 1 finishes the grace period is long expired, and at that exact instant `RunsFilter` legitimately shows zero other non-terminal `master_pipeline` runs (run 2 hasn't been submitted yet) — the sleep sensor's own "safe to unpause" condition, satisfied by construction, not bad luck. This is a structural, near-guaranteed race in the existing mechanism, not a fluke.

**Checked against Dagster's own documented practice** (its Helm chart, published multi-code-location scaling case studies) rather than hardening the heuristic further: production Dagster-on-Kubernetes deployments don't scale webserver/daemon/code-server to zero at all — they're treated as small, always-on singleton Deployments. Real elasticity in a mature Dagster+K8s deployment happens one layer down (ephemeral per-run Job pods, already how this project's `EXTRACTION_JOBS`/`MODELING_JOBS`/`SERVING_JOBS` work) and one layer further down still (node/cluster-autoscaler shrinking the underlying node pool, not application pods). If genuine scale-to-zero for a singleton control-plane API is ever wanted later, the production-grade mechanism is a request-queueing proxy in front of it (KEDA's HTTP Add-on, Knative's Activator) that buffers a request during cold start instead of passing it to a pod that isn't there — a materially larger, separate piece of infrastructure, not a smaller version of the annotation-based approach that was here.

**Resolution — reverted to always-on, removed the mechanism entirely, not just disabled it**: `dagster-webserver`/`dagster-daemon`/`dagster-code-server` are now plain `replicas: 1` Deployments, no KEDA involved. Deleted: `orchestration/k8s/keda-scaledobjects.yaml`, `orchestration/k8s/rbac-frontend-wake.yaml`, `wake_sleep_sensor.py` + its test, `frontend/dagster_wake.py` + its test, `platform/namespaces/keda.yaml`, `frontend/k8s/serviceaccount.yaml` (existed solely for the wake mechanism's cross-namespace RBAC grant — frontend reverted to the namespace's shared `default` ServiceAccount). Removed `install-keda`, `_wake-orchestration`, `_sleep-orchestration` from `orchestration/module.just`, their invocations from `verify-pipeline`/`verify-schedule`/`verify-sensor`, and the `keda.sh`/`scaledobjects` RBAC grant from `orchestration/k8s/rbac.yaml`. `definitions.py` no longer registers `ALL_WAKE_SLEEP_SENSORS`. `frontend/pages/6_Trigger_Pipeline.py` no longer calls `wake_orchestration()` before submitting. Docs updated to match: `README.md`, `Roadmap.md`, `Backlog.md` (dropped the now-moot grace-period and KEDA-Cron-windows entries) had every reference removed; `Learnings.md`'s three separate KEDA-race entries were consolidated into one short entry, "Dagster control plane scaling on Kubernetes," covering what was tried, what went wrong, and why the mechanism was abandoned rather than hardened further.

**A second, unrelated issue surfaced during this same runtime verification and was fixed alongside it**: the first `just start` after this work failed at Polaris catalog bootstrap with `default-base-location 's3://lakehouse' is not within any of the allowed locations [s3://lakehouse/*]` — confirmed via the running pod's own startup log (`polaris-server 1.7.0`) that `apache/polaris:latest` had silently pulled a newer Polaris release than whatever last worked, since `query-engine/polaris/deployment.yaml` had no version pin and Kubernetes defaults an unpinned `:latest` tag to `imagePullPolicy: Always`. Two fix attempts: a trailing slash on `default_base_location` alone (`bootstrap.py`) didn't satisfy 1.7.0's tightened validation; listing the bucket root literally in `allowed_locations` alongside the `/*` glob (`allowed_locations=["s3://lakehouse/", "s3://lakehouse/*"]`) did. Given the demonstrated risk of unpinned off-the-shelf images, every floating image/Helm chart in the project was pinned to its now-confirmed-working version in the same pass: `apache/polaris:1.7.0`, `apache/polaris-admin-tool:1.7.0` (verified via `--version` that `:latest` and `:1.7.0` report the identical Polaris version despite a different image digest — a base-image layer rebuild, not a different release), `minio/minio:RELEASE.2025-09-07T16-13-09Z`, `minio/mc` pinned by digest (no clean semver tag exists matching its own reported version), `apache/kafka:4.3.1` (digest-verified identical to what `:latest` resolved to), Trino's Helm chart pinned to `1.42.2` (`--version` flag added to `query-engine/trino/module.just`), and the Flink Kubernetes Operator's chart pinned to `1.15.0` (`streaming/flink/module.just`). `postgres:16` was already pinned, no change needed there.

**Verified live, repeatedly, not just by reasoning about the fix**:
- `orchestration::verify-pipeline`/`verify-schedule`/`verify-sensor` all pass clean — zero `ConnectionResetError`/`TransportConnectionFailed` — both immediately after the mechanism was removed and again after every image/chart was pinned and the cluster rebuilt from zero a second time.
- Deliberately went further than the existing verification tooling: fired all three `master_pipeline` runs (`model_schema=sales`, `model_schema=metadata`, `batch_group=police_crimes`) truly *concurrently* (parallel subprocesses, not `verify-pipeline`'s own sequential pattern) via `trigger_master_pipeline` directly — all three succeeded, zero connection errors. This is a harder test of the same failure mode than anything the mechanism was ever previously exercised against.
- `frontend/tests/test_trigger_pipeline_page.py` (trimmed of its now-dead `force_cold_start` fixture and cold-start test, which tested the removed mechanism) passes clean against the live cluster, confirming the Trigger Pipeline page works correctly with no wake call anywhere in its path.
- `just kill` torn down clean with zero KEDA references anywhere in its output (grep-confirmed).
- Hit the recurring iCloud `.pth`/`UF_HIDDEN` `ModuleNotFoundError` signature twice during this session's repeated `just start` cycles (`domain_naming` module) — handled per CLAUDE.md's standing instruction both times (`rm -rf .venv && uv cache clean && uv sync --all-packages`, no diagnosis), not treated as a real regression.

**Caveat**: `Bash` background-task completion notifications reporting `exit code 0` for a `command | tee file` pipeline reflect `tee`'s own exit status, not the piped-in command's, when `pipefail` isn't set — this was confirmed to matter for real: a `just start` failure was initially missed because the notification said success while the log itself ended in `error: Recipe start failed`. Every backgrounded `just`/multi-step command in this session going forward should set `pipefail` before piping through `tee`, and the log's own tail should be checked directly rather than trusting the reported exit code alone.

**Also produced this session**: `.claude/settings.json` (new, project-shared) — a permission allowlist covering commands that don't need per-call approval, derived from actual transcript usage plus explicit user sign-off for broader categories (`python3`, `psql`, `tee`, `just *`, `grep *`, and a few `uv run`/`cd`-scoped patterns). `CLAUDE.md` gained one new absolute rule (user-authorized direct edit, not routed through the normal doc-ownership matrix): once work is already authorized, only stop for destructive commands or commands operating outside this project's own directory — not for every individual routine command.

**Follow-up in progress, not yet landed as of this entry**: a QA-agent task to write a Gherkin `.feature` spec plus real pytest in `tests/integration/` for two design principles this work re-confirmed — pipeline runs must be independent of shared infrastructure (the concurrent-trigger stress test above, made permanent), and the Dagster control plane must stay at a fixed `replicas: 1` with no scale-to-zero mechanism, matching Dagster's own documented Kubernetes deployment pattern.
