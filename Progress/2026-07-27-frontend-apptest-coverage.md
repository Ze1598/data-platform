# Full frontend `AppTest` coverage + `8_Debug_Model_Query.py` (2026-07-27)

Closes the runtime-validation gap left open by `Progress/2026-07-27-documentation-audit.md`, plus a broader one: three of the seven frontend pages (`1_Source_Systems.py`, `2_Data_Feeds.py`, `3_Lakehouse_Models.py`) and two more (`4_Ingestion_Triggers.py`, `5_Streaming_Sources.py`) had zero `AppTest`-level coverage at all — only `6_Trigger_Pipeline.py`/`7_Model_Table_Columns.py` did. New test files (`test_source_systems_page.py`, `test_data_feeds_page.py`, `test_lakehouse_models_page.py`, `test_ingestion_triggers_page.py`, `test_streaming_sources_page.py`) cover every remaining page's real validation rules (ODS-domain 1:1 conflict, sensor/connector-kind eligibility, `deletes_enabled` requiring full extraction, etc.), not just "loads without exception," verified against a genuinely fresh `just nuke`+`just start` cluster.

**Real, reusable finding**: `streamlit.testing.v1.AppTest`'s success-message capture is unreliable across any page action that calls `st.success()` immediately followed by `st.rerun()` — which is every Add/Edit/Delete flow in this app. Confirmed by direct reproduction (an otherwise-identical schedule-vs-sensor add flow on the same page captured the message in one case and silently dropped it in the other, both times the underlying write succeeded correctly). Fixed by asserting the actual database outcome instead of the transient message, per this repo's own already-stated lesson ("verifying the submission call succeeded is a materially weaker claim than verifying the thing it submitted actually completed"). `at.error`/`at.exception` remain reliable (the error path never reaches `st.rerun()`).

The one Kafka-dependent test (`test_streaming_sources_page.py::test_discover_schema_writes_correct_created_by_tag`) skips cleanly host-side (Kafka's Service is ClusterIP-only, same reason `streaming/testing/` runs as in-cluster Jobs) but was confirmed to actually pass by `kubectl cp`-ing the test file into the running `frontend` pod and running it there directly against the real `sales_events` topic.

**New page, `frontend/pages/8_Debug_Model_Query.py`**: an ad hoc Trino query tool — pick any table in the `model` schema, see its first 500 rows (`SELECT * FROM iceberg.model.<table> LIMIT 500`), for confirming a pipeline run actually populated it. Needed a real connection this app didn't have before (`model` lives in Trino/Iceberg, not the Postgres metadata DB every other page reads) — added `trino>=0.330` to `frontend/pyproject.toml` and `TRINO_HOST`/`TRINO_PORT` env vars (`trino.query-engine.svc.cluster.local:8080`) to `frontend/k8s/deployment.yaml`, mirroring the same env-var pattern already used for `POSTGRES_HOST`/`DAGSTER_WEBSERVER_HOST`. Verified live: rebuilt/redeployed the frontend image, confirmed via `kubectl exec` that the running pod actually has the new page file and `trino` importable, then triggered a real `master_pipeline` run (hit the already-documented Backlog.md `ConnectionResetError` KEDA-wake race once, succeeded on retry per that entry's own established practice) to populate `model` with real data (`sales_dim_branch`, `sales_fct_sales`, `police_crimes` at 216,828 rows, etc.) and confirmed the page renders it correctly.
