# Remove `lakehouse_model_columns` — redundant metadata table, not an integration bug (2026-08-19)

Started from Backlog.md's "`lakehouse_model_columns`-driven dedicated staging generation doesn't integrate with `deletes_enabled`" — a model with `lakehouse_model_columns` rows and `deletes_enabled=true` got its dedicated `stg_<table_name>.sql` silently skipped, falling back to feed-named staging, because deletion synthesis (`generate_deletion_synthesis_views.py`) still hardcoded `stg_<feed_friendly_name>` and never learned about the newer per-model staging mechanism.

**Investigation initially over-scoped the fix**: grepping every `ref('stg_...')` against `lakehouse_models` found 5 files pointing at feed-named staging, not the 1 the backlog item named. Read as "staging is being shared across models when it shouldn't be," which would have meant migrating 3 hand-authored fact/dimension files (`sales_dim_branch.sql`, `sales_fct_sales.sql`, `sales_fct_daily_financial_activity.sql`) plus `metadata_fct_runs.sql` to per-model staging files with no existing typed-cast template to build from. Wrong: `metadata/DataModel.md:184` already documented feed-named staging as legitimate, "distinct from the pre-existing per-feed `stg_<feed>.sql` staging models, which stay shared/hand-written and unaffected." Those 4 files were correct as-is — none had `lakehouse_model_columns` rows, so free-text-flow shared staging was exactly right for them.

**Root cause reframed, not just the narrow bug fixed**: `lakehouse_model_columns` carried no information not already derivable from `lakehouse_models` plus its generated code — a second table describing a model's columns, built independently of and never reconciled with the first, is what produced the integration bug in the first place. Decision: remove the table entirely rather than integrate it more deeply, plus the Streamlit page built around it (`frontend/pages/7_Model_Table_Columns.py`).

**Removed**: `lakehouse_model_columns` table (DDL in `metadata/db/init/01_platform_metadata.sql`, dropped live), `generate_model_scaffolds.py`'s dedicated-staging generation path (`fetch_model_columns`/`_cast_expr`/`_render_dedicated_staging`/`staging_target_path`, and the three-way branch in `generate()` collapsed to one), `frontend/pages/7_Model_Table_Columns.py` and its test, `frontend/metadata_db.py`'s `fetch_lakehouse_model_columns`/`replace_lakehouse_model_columns`, `scripts/seed_metadata_db.py`'s `seed_lakehouse_model_columns`. Updated `tests/integration/test_utc_consistency.py`'s staging-name lookup to re-derive the same coverage (a model aliasing its staging by `table_name` instead of feed name) through `lakehouse_models.depends_on_feeds` instead of the removed table — so the one real production case using that pattern (`iot_telemetry_dim_device`) stays test-covered, not silently dropped. Docs updated: `README.md`, `Backlog.md` (deleted the now-resolved item and the now-moot "Frontend page for defining model tables — needs a rebuild" item), `metadata/DataModel.md`.

**One live data inconsistency found and fixed in passing**: `dim_iot_device`'s `lakehouse_models` row had empty `business_key_columns`/`tracked_columns` — the real values (`device_id` as key; `battery_level`/`signal_strength`/`firmware_version` tracked) only ever lived in the now-removed table, baked once into the already-generated `.sql` files and never backfilled into `lakehouse_models` itself. Synced live and in `seed_metadata_db.py` so the metadata now matches what the generated files actually build.

**Verified at runtime, not just by test suite**: `generate-model-scaffolds`/`generate-deletion-synthesis-views` both ran clean against the live platform post-removal. Full test suite green: frontend 48 passed/1 skipped, `tests/integration` 18 passed, `orchestration` 14 passed, `dbt test` across all 4 domains 67 passed, `processing` 11 passed.
