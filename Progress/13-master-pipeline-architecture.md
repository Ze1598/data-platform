# Phase 13 — Master pipeline architecture (extraction/validation/transformation/serving)

- [x] Extraction/validation split: generic connector library (`processing/connectors/`), schema discovery relocated to extraction time, `raw_to_clean.reconcile_schema()` narrowed to pure validation-time coercion
- [x] `metadata_runs`, `financial_transactions`, `police_crimes` migrated onto the connector library
- [x] Master pipeline built as a real Dagster construct: `pipeline_init_<feed>` (generated for every feed), the actual entry point that registers the run and resolves selected steps
- [x] Cherry-picking: `pipeline_steps` lookup table + `data_feed`/`lakehouse_models` selection columns, live per-run gating (extraction/validation/transformation) and codegen-time gating (per-model serving)
- [x] dbt build split into two independently selectable invocations per feed (transformation, serving)
- [x] Frontend CRUD updated (`2_Data_Feeds.py`/`3_Lakehouse_Models.py` pipeline-steps multiselect)
- [x] dbt-side boilerplate reduction: `scripts/generate_model_scaffolds.py` generates Type 1 dimension/fact `.sql` models and Type 2 dimension snapshot `.sql` files (plus a matching per-model `.yml` test companion) from `lakehouse_models`, for any active row whose target file doesn't exist yet — full `config()`/`row_hash()`/`classify_changes()`/technical-column boilerplate pre-filled, only the `base`/`hashed` select's real business logic left as a placeholder
- [x] Per-model transformation gating — resolved via a different mechanism than originally scoped: the ODS (Operational Data Store) layer. See Part 4 below and Backlog.md's superseded note.

Notes / deviations:

This phase split into two addenda (full design in `.claude/plans/i-want-to-create-calm-manatee.md`), and the second only happened because the first, on its own, didn't actually deliver what had been asked for.

**Part 1 — connector library.** Built `processing/connectors/`: `TabularConnector`/`JsonConnector` base classes, `PostgresConnector`/`CSVConnector`/`RestConnector`/`JsonFileConnector`, `infer_column_definitions()` (generic schema discovery) and `compute_schema_sync()` (pure diffing, deciding whether discovery represents a real change). `PostgresMetadataResource.sync_schema_registry()` owns the I/O side. `write_clean_snapshot()` was changed to self-determine schema changes by comparing the live Iceberg schema, instead of requiring a caller-computed flag — needed because discovery and the write that consumes it are no longer guaranteed to happen in the same function. `metadata_runs` (previously only reachable via `Walkthrough_Metadata_Source_Feed.md`'s manual SQL) is now reproducibly seeded for the first time.

**Real bugs found in part 1:**
1. `metadata_runs` genuinely has nothing to report on a fresh cluster's first run (it queries `data_processing_runs`, empty before any run completes) — `clean_metadata_runs` correctly saw an empty batch and never created `clean.metadata_runs`, so the downstream dbt build failed with `TABLE_NOT_FOUND`. This wasn't a bug to route around — see part 2, `record_run_started()` closes it properly.
2. `dbt_assets.py`'s `_CLEAN_SOURCE_TABLES` (a hand-maintained set determining which dbt sources map onto their `clean_<feed>` Dagster asset) was never updated for the new `metadata_runs` feed — without it, Dagster never wired a real dependency between `clean_metadata_runs` and its dbt build, letting dbt race ahead of the write it depended on. The actual root cause; everything else that looked broken in the same run was collateral from this one failure aborting the whole run.
3. `stg_financial_transactions.sql`'s `posted_date` cast failed on real CSV data (`Value cannot be cast to timestamp: 2026-07-10T23:17:02Z`) once discovery started recording it as `string` (matching what Polars actually observes — CSV values are just strings, schema inference has no way to know one is meant to be a timestamp). First attempt at a fix was wrong: adding feed-specific datetime-parsing knowledge into `CSVConnector`, breaking the "connectors stay fully generic" principle. Corrected: `schema_registry` is the source of truth for raw/clean only, never staging — the cast belongs in `stg_financial_transactions.sql` itself (`from_iso8601_timestamp(...)`, not a plain `cast`), matching the same pattern the model already used for `account_code`.

**Part 2 — the master pipeline itself.** Point-blank question surfaced the real gap: *"did you or did you not create a master pipeline that contains the 4 stages and the respective children pipelines designed?"* — answer was no. The four steps (extraction/validation/transformation/serving) existed only as design prose (now README.md's "Master Pipeline Architecture"); the actual code was still organized entirely around the older six-value schema vocabulary (`landing`/`raw`/`clean`/`staging`/`model`/`serve`). Built for real: `pipeline_steps` lookup table (same shape as `load_type`) — explicitly **not** the same axis as the six schemas `data_processing_runs` tracks (a pipeline step can span multiple schemas; `data_processing_runs` is unchanged, still schema-level). `pipeline_init_<feed>`, generated for every feed (connector-driven and hand-written alike), is the real entry point: calls `record_run_started()` (moved out of the individual landing assets) and resolves the feed's selected steps live, once per run. Every stage-owning asset checks membership before doing real work, leaving the corresponding `data_processing_runs` columns genuinely `NULL` (not "successful with zero rows") when a step is deselected.

**Real bugs found in part 2** (three of these were the same underlying misdiagnosis, corrected in sequence across several `just smoketest` cycles):
1. A stale `DBT_ASSETS` import survived in `financial_assets.py` after the dbt-assets factory split — mechanical, caught immediately by the import error.
2. `path:` dbt selectors, used to distinguish "transformation" from "serving" nodes, silently matched zero nodes when evaluated *inside* `@dbt_assets(select=..., exclude=...)` — confirmed by reading `dagster_dbt`'s own source: that decorator resolves selectors **in-process**, against a synthetic `Manifest` object built directly from JSON with no real project root, which a `path:` selector needs to resolve a relative filesystem path. The identical selector string worked correctly via the real `dbt ls`/`dbt build` CLI (a completely different code path with real project context) — which is exactly why the first "fix" (correcting the path string based on the manifest's own `path` field) still failed identically. Resolved by switching to `tag:` selectors (`generate_serve_views.py` now tags every generated view with a second `serving_layer` tag) — pure attribute matching, no project-root dependency.
3. `verify-schedule`'s `run_id=$(...)` bash capture broke once (2) was fixed — resolving `path:`/`tag:` selectors that genuinely match zero nodes (e.g. `police_crimes`, which owns no `lakehouse_models` rows) makes dbt print a warning straight to stdout, and that warning fires at Python *import* time (any process importing `pipeline_generated.py`, including the standalone `trigger_schedule_run.py`) — corrupting the captured run id into multi-line garbage even though the underlying k8s Job completed successfully every time. Fixed with `| tail -1` (`print(run_id)` is always the script's last line for a feed-type schedule).

**Deliberate scope decision**: per-model transformation gating (a single model opting out of transformation while its sibling models under the same feed still build) was explicitly not built — today's dbt build is scoped per *feed*, not per model, and doing this properly would mean a dynamic per-model `--exclude` list inside each feed's transformation invocation. Only per-model *serving* is gated (resolved at codegen time by `generate_serve_views.py`, simply not generating a model's views). Noted in `Backlog.md`.

**Verified live**: full `just smoketest` (genuine nuke, rebuild) green across every check. Beyond the automated suite, cherry-picking was verified directly against the running cluster: `police_crimes` narrowed to `pipeline_steps='0,1'` (extraction+validation only), triggered via `dagster job launch`, confirmed `is_landing_successful`/`is_raw_successful`/`is_clean_successful` all `true` with real row counts while `is_staging_successful`/`is_model_successful`/`is_serve_successful` stayed `NULL` and no `data_processing_runs` model-row was created at all for that run; `dim_branch`'s `pipeline_steps` narrowed to `'2'` (no serving), regenerated, confirmed its `_latest`/`_historical` files disappeared while every other model's stayed. Both reverted to defaults, confirmed restored, before final teardown.

**Part 3 — dbt-side boilerplate reduction (`scripts/generate_model_scaffolds.py`).** Closed the last open Phase 13 item. Follows the same shape/conventions as `generate_serve_views.py`/`generate_deletion_synthesis_views.py` (`CONN_KWARGS`, `REPO_ROOT`, plain Python f-string templates, no jinja2), wired into `orchestration::start` alongside the other three `generate-*` steps. Genuinely different from its siblings in one respect: every other codegen script in this project fully wipes-and-regenerates its output directory on every run, because that output is 100% generated. This script's output is a permanent *mix* of generated boilerplate and hand-written business logic in the same file, so it does the opposite — for each active `lakehouse_models` row, if the target file already exists it's left completely untouched forever (even after the row is later deactivated); only a missing file gets scaffolded. `table_type='fact'` and `scd_type=1` dimensions render a regular model `.sql` under `models/model/{dimensions,facts}/`; `scd_type=2` dimensions render a dbt snapshot under `snapshots/` instead. `deletes_enabled` governs `is_deleted` sourcing (from the already-existing, separately-generated `int_<feed>_with_deletes.sql` intermediate) independent of `scd_type` — same branch condition applies to both the Type 1 and Type 2 templates. FK-join boilerplate (a fact joining a dimension's `_key_hash`) is deliberately left out — no metadata describes which dimension to join or on what key, so that stays genuine hand-written logic like the rest of `base`.

Schema-test entries for a new model go into a per-model companion `.yml` file next to the scaffolded `.sql`/snapshot (e.g. `dim_product.yml` beside `dim_product.sql`), not merged into the existing shared `models/model/schema.yml` — a real architectural fork, resolved via direct user choice over the alternative (safely parsing and merging into the shared file, which would've needed a new YAML-library dependency and merge logic that must never touch the ~200 lines of hand-written comments/tests already there). The companion-file approach reuses the exact same write-if-missing mechanism as the `.sql` file and needs no new dependency.

**Real, confirmed sharp edge (not a bug, but worth being explicit about)**: `dbt parse` hard-errors ("dbt found two schema.yml entries for the same resource") if a model's name appears in property blocks in two separate YAML files. This can't happen through normal use of the script — a companion `.yml` only gets created for a genuinely new model, which by definition has no pre-existing shared-`schema.yml` entry to collide with — but was hit for real during the rehearsal-test verification below (see next paragraph), and is now documented directly in the script's own docstring so a future "delete a `.sql` file by hand without also removing its `schema.yml` entry" mistake is understood rather than mysterious.

**Part 4 — the ODS (Operational Data Store) layer.** Resolved Phase 13's last remaining item (per-model transformation gating) a different way than originally scoped: rather than build a dynamic per-model `--exclude` list inside a feed's dbt build, a feed that never gets a hand-modeled dimension/fact can instead deliver an automatic ODS table — `clean` data pushed as-is (no casts) through a fully auto-generated `staging` + Type 1 `model` layer, driven purely by `schema_registry`. Also corrected the "skip serving" framing from earlier Phase 13 work: the real rule is "skip *automatic* view generation," not "skip the serving layer" — an ODS table still gets standard `_latest`/`_historical` views, since consumers must never touch `model` directly.

New DDL: `data_feed.ods_enabled` (explicit flag; silently ignored if the feed already owns any `lakehouse_models` rows — those take precedence, treated as "forgot to disable it," not an error) and `schema_registry.primary_key_columns` (the resolved primary key, precedence `data_feed.source_pk` → a live-discovered key → empty/insert-only, persisted at schema-sync time so runtime reads one source of truth). `PostgresConnector` gained real catalog introspection (`discover_primary_key()`, `pg_index`/`pg_attribute`, only when given a single real `table_name` — gracefully returns `None` for a multi-table query like `metadata_runs`'s, without attempting one). New `scripts/generate_ods_models.py` (fully regenerates every run, unlike `generate_model_scaffolds.py` — ODS has zero hand-written content ever, so nothing needs protecting) generates both layers per `ods_enabled` feed; `scripts/generate_serve_views.py` extended with `fetch_ods_feeds()` to generate the same standard views for ODS tables.

**Two related automation gaps closed along the way, by explicit direction** (not originally scoped, but the same category of problem this session was already fixing): `models/staging/_sources.yml` (dbt's `clean` source declarations) was hand-maintained, silently failing `dbt parse` for any new feed until someone remembered to add an entry — now `scripts/generate_sources.py`, fully regenerated from `data_feed` every run. `dbt_assets.py`'s `_CLEAN_SOURCE_TABLES` had the identical problem (a hardcoded set needing a manual entry per new feed) — now generated into a small standalone `clean_source_tables_generated.py` by `scripts/generate_dagster_pipeline.py` (a separate file, not folded into `pipeline_generated.py` itself, specifically to avoid a circular import: `pipeline_generated.py` already imports from `dbt_assets.py`).

**A real bug found and fixed during live verification, not by inspection**: the original insert-only design ("no key → plain incremental append, safe because `clean` is a per-run atomic overwrite") is only true for `extraction_type='incremental'` feeds. For `extraction_type='full'` feeds with no key, `clean` re-delivers the *complete* dataset every run — plain append duplicates every previously-seen row on every run. Confirmed for real: a 2-row JSON batch became 6 rows after two runs before this was caught. Fixed by branching `generate_ods_models.py` on `extraction_type` for the no-key case: `incremental` → plain append (unchanged, correct); `full` → `materialized='table'` (full replace every run, mirroring `clean`'s own per-run-snapshot semantics — also honest about what's achievable without a key, since there's no way to detect a real change without one anyway).
