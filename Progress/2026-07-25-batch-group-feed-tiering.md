# Batch-group feed tiering by `batch_feed_hierarchy` (2026-07-25) — built and live-verified

Closes the `Backlog.md` item "`batch_group`/`batch_feed_hierarchy` are metadata-only": a `batch_group`-triggered `master_pipeline` run now extracts feeds tier by tier, in parallel within each tier, instead of one feed at a time regardless of hierarchy. `data_feed.batch_feed_hierarchy` had no real multi-feed batch to run against, so this also seeded one, real, to prove the mechanism rather than build it speculatively.

Ordering model builds (staging+model dbt runs) by `lakehouse_models.depends_on_feeds`/`batch_hierarchy` instead of waiting for a batch's entire extraction phase to finish is a separate, unrelated feature — see Roadmap.md's "Dependency-driven model build pipeline for `lakehouse_models`" — not a continuation of this one.

- **`PostgresMetadataResource.get_batch_group_feeds_by_tier()`** (replacing `get_batch_group_feeds()`) discovers distinct `batch_feed_hierarchy` values for a batch group directly from Postgres and returns `(tier, feeds)` pairs ascending — no fixed tier count, spacing, or starting value assumed; a batch group with every feed at the same hierarchy value is valid and yields one tier.
- **New `dagster_launch.launch_many_and_wait()`**: submits every job in a tier up front (concurrent `K8sRunLauncher` pods), polls all to a terminal status, and only then raises if any failed — a tier's own siblings are never cancelled by one another's failure, only the next tier is blocked from starting.
- **`run_master_pipeline`'s extraction loop** (`scripts/generate_dagster_pipeline.py`'s codegen template) now iterates `feed_tiers` ascending for `orchestration_kind='batch_group'` runs, launching each tier via `launch_many_and_wait`. `model_schema` runs are unaffected (resolve to a single synthetic tier, same sequential behavior as before) — tiering is a `batch_group`-only mechanism, matching the Roadmap proposal's own scoping.
- **New `iot_telemetry` batch group** seeded to actually exercise this: 6 synthetic IoT telemetry feeds (`device_heartbeats`/`device_errors` @ tier 1, `session_events`/`location_pings`/`network_usage` @ tier 2, `device_health_snapshots` @ tier 3) under a new `iot_telemetry_landing` source system (`connector_kind='json_file'`) — JSON files dropped into `data-lake/landing/<feed>/` rather than a real external system, extraction-only (no ODS domain, no `lakehouse_models` consumer), specifically to keep this test scoped to the feed-tier mechanism. Each feed has its own thin `JsonFileConnector` subclass (`orchestration/dagster_data_platform/dagster_data_platform/connectors/<feed>_connector.py`) with a pass-through `flatten()` (the synthetic JSON is already flat, unlike `police_crimes`' real nested API response).
- **`seed_data_feed()` gained a `batch_feed_hierarchy` parameter** (`scripts/seed_metadata_db.py`), defaulting to `0` (matching the DDL default) — every pre-existing feed's seed call is unaffected.
- **Stale docstring fixed in passing**: `get_batch_group_feeds()`'s old docstring referenced a nonexistent `pipeline_generated.py` function, `resolve_run_plan_for_batch_group()` — never existed in the actual generated code, corrected while rewriting the method it was attached to.

**Live-verified** (real `kind` cluster, not a dry run): seeded the new batch group, regenerated `pipeline_generated.py`, rebuilt/restarted orchestration, dropped real JSON files into all 6 feeds' landing directories, and triggered `orchestration_kind=batch_group orchestration_value=iot_telemetry` via `trigger_master_pipeline`. Run `6f18e6aa-4aae-47df-841c-8d12ef23de17` succeeded end to end; `data_processing_runs` timestamps confirm both properties this change is meant to guarantee, not just that the run happened to succeed:
- **Tier ordering held**: tier 1's two feeds both ended ~18:32:49 UTC; tier 2's three feeds only ended ~18:33:09 (~20s later, consistent with tier 2 launching only once tier 1 fully finished); tier 3's one feed ended ~18:33:27 (~18s after tier 2).
- **Parallel-within-tier held for real, not just trivially**: tier 2's three feeds (`session_events`/`location_pings`/`network_usage`) ended within roughly 1ms of each other (`18:33:09.322033`/`.322022`/`.32215`) — sequential execution would have spread these apart by each job's own runtime, not converged them.
- Raw + clean stages succeeded for all 6 feeds with exact row counts matching the seeded JSON (3/2/3/2/3/3), confirming this wasn't a zero-row no-op success.

Hit the project's known `.pth`/`UF_HIDDEN` race once mid-implementation (`ModuleNotFoundError: No module named 'domain_naming'` on `just orchestration start`, after the `kind` cluster's Docker container had been stopped and freshly restarted for this session) — fixed per the standing rule (`rm -rf .venv && uv cache clean && uv sync --all-packages`), no diagnosis needed, then the full `start` sequence succeeded clean on retry.

Model-tiering (the other half of the Roadmap proposal) remains unbuilt — see Roadmap.md, which now reflects this split status.
