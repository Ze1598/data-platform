# Phase 6 — real raw→clean (Polars default, Spark opt-in)

- [x] `data_feed.processing_engine` metadata column (`'polars'` default, `'spark'` opt-in)
- [x] `processing/raw_to_clean/` uv workspace member implemented (PyIceberg for catalog I/O, Polars for transformation — not a PySpark job; see Notes)
- [x] Schema validation against `schema_registry` implemented and verified to actually reject bad data (missing columns, wrong type, null in a non-nullable column), not just accept good data
- [x] Stub `clean_sales` asset replaced with a real PyIceberg + Polars write (`table.overwrite()`, one atomic commit)
- [x] **Verify**: triggered via the real `K8sRunLauncher` path (`dagster job launch`, not `dagster asset materialize`), confirmed a real pod launched and completed in `kubectl get pods -n orchestration`, confirmed all 8 `run_audit_log` rows (both feeds) with correct status/row counts, confirmed `staging.customers`/`staging.sales` row counts match

Notes / deviations:
- **Scope change from the original Roadmap, decided with the user before implementation, not a workaround**: Spark/`spark-operator` deferred; **Polars is the default processing engine** (runs inline in the Dagster op/pod, no separate CR or cluster infrastructure), **Spark becomes opt-in per feed** once actually needed for volume, selected via the new `processing_engine` metadata column. No `spark-operator` deployment exists yet — not needed for the default path. Full reasoning in Learnings.md.
- **Read/write goes through PyIceberg directly, not Polars' own `write_iceberg()`** — checked Polars' current stability status first (real progress: `sink_iceberg()` landed in 1.39; `write_iceberg()` still formally unstable). PyIceberg owns the catalog/storage boundary, Polars owns in-memory transformation — explicit separation of concerns, and `table.overwrite()` is a single atomic Iceberg commit, unlike the Phase 5 stub's `DELETE`+`INSERT`. This closes the exact concurrency gap the Phase 5 pools were built to guard against, not just add a second layer of protection on top of it.
- **New feed added: `sales` (supermarket transactions)**, alongside `customers` — a `source_system` (`supermarket_pos`) + `data_feed` + `schema_registry` entry (15 columns: `invoice_id`, `branch`, `city`, `customer_type`, `gender`, `product_line`, `unit_price`, `quantity`, `tax_amount`, `total`, `payment_method`, `cogs`, `gross_income`, `rating`, `sale_timestamp`), plus `landing_sales`/`raw_sales`/`clean_sales`/`stg_sales` assets mirroring the `customers` chain. Deliberately real/realistic (not trivial) data specifically to exercise genuine schema validation — multiple types (string/long/double/timestamp), a nullable field, a natural business key. Also the first real test of whether this project's per-feed patterns (concurrency pools, `run_audit_log`, dbt tagging) actually generalize past one feed, not just work for the one they were designed against.
- Adding a second feed's dbt model immediately hit a scaling boundary Phase 5 had explicitly flagged as anticipated-but-not-yet-real: one `@dbt_assets` function running `dbt build` project-wide would wrongly serialize unrelated feeds under one concurrency pool. Fixed by splitting into one `@dbt_assets` function per feed (tag-based dbt selection + per-feed pool) — see Learnings.md for the mechanism.
- landing/raw remain stubs for both feeds (in-memory only, no real file writes) — real raw file writes are still out of scope; this phase was specifically about raw→clean becoming real, matching its own name.
- `processing/raw_to_clean/` is a **library**, not a standalone deployment — imported directly by `orchestration` as a workspace path dependency (same pattern as `polaris_client`), executed inside the same Dagster op/pod that already runs via `K8sRunLauncher`. No new namespace, no new image beyond what `orchestration`'s own Dockerfile already builds.
- **UTC consistency fix, post-implementation**: `clean_customers` was still writing via the old Trino `DELETE`+`INSERT` stub (never migrated when `clean_sales` was built), leaving it as a naive `timestamp(6)` while `sales` was correctly `timestamp(6) with time zone`. Migrated `clean_customers` onto the same `raw_to_clean` path as `clean_sales` — same fix that closes the last remaining `DELETE`+`INSERT` race, and gives `customers` real `schema_registry` validation for the first time. `TrinoResource` was fully unused afterward and removed. Required dropping and recreating both `clean.customers` and the *pre-existing* `staging.customers` (dbt's incremental `MERGE` doesn't retroactively fix an existing table's column types) — re-verified end-to-end through the real `K8sRunLauncher` path afterward, all 8 `run_audit_log` rows correct, both tables now genuinely `with time zone`. Full story in Learnings.md.
- **New**: `scripts/seed_metadata_db.py` — the `source_system`/`data_feed`/`schema_registry` rows for both feeds had only ever existed as ad hoc `psql` commands, not reproducible. Idempotent, covers everything seeded so far, new workspace member.
- **New**: `tests/integration/` — first real regression test (`test_utc_consistency.py`), metadata-driven (checks whatever feeds `schema_registry` currently has, not a hardcoded list) against the live platform. New workspace member.
- **Process hygiene, standing rule from here on**: kill `dagster dev`/port-forwards and stop the kind cluster (`docker stop`, not delete) once a phase's work is done; restart fresh next time, including mid-phase if code needs testing again. See Learnings.md.
- **Tech debt removed**: `metadata/db/init/04_processing_engine.sql` (an incremental `ALTER TABLE` migration file) deleted; `processing_engine` folded directly into `01_platform_metadata.sql`'s original `data_feed` definition. Project has no production data to preserve, so migration-style SQL files are unnecessary debt — schema changes go straight into the original table definition.
- **Full cluster nuke-and-rebuild validated as the project's standing regression-testing methodology, not a one-off check**: `kind delete cluster` → full rebuild from zero (Postgres → MinIO → Polaris → catalog registration → Trino → metadata seed → orchestration image → `dagster dev` → full pipeline) surfaced two real bugs that every prior incremental test had silently missed because leftover state from earlier phases masked them:
  - **Bug 1**: `write_clean_snapshot()` assumed the `clean` namespace already existed (true on every previously-reused cluster, false on a genuinely fresh one). Fixed with `catalog.create_namespace_if_not_exists(namespace)` before `create_table()` in `raw_to_clean/write.py`.
  - **Bug 2**: `dbt_customers_assets` and `dbt_sales_assets` run in separate concurrency pools by design (Phase 6, above) — on a fresh catalog with no `staging` namespace yet, both raced to implicitly create it via dbt-trino, and Trino's implicit schema-creation isn't safe under that race (unlike PyIceberg's namespace creation, proven safe by Bug 1's fix). Fixed by pre-creating both `clean` and `staging` namespaces once, deterministically, in `polaris_client/bootstrap.py` (run via `register-catalog.sh`) — removes the race entirely rather than relying on concurrent runtime code to handle it safely. `polaris_client` gained a workspace dependency on `raw_to_clean` for this.
  - **Verify**: re-ran `register-catalog.sh` (both namespaces created cleanly), rebuilt+reloaded the orchestration image, full pipeline run completed with `RUN_SUCCESS` and all 8 `run_audit_log` rows `success` on the first attempt after the fix; `tests/integration` re-run against the same fresh cluster, still `2 passed`.
  - **Known gap, closed next**: `scripts/bootstrap_kind.sh` only covered cluster+namespaces+Postgres at the time — the rest of this rebuild was driven by hand from each module's `DebugReference.md`. Closed by the `just`-based tooling below.
  - Full story in Learnings.md.
- **`just`-based operational tooling**: root `Justfile` + one `module.just` per module (`platform`, `metadata`, `minio`, `polaris`, `trino`, `query-engine` composite, `orchestration`, `processing`, `dbt`, `frontend`, `tests/integration`) — `just start`/`kill`/`nuke`/`smoketest`/`test`, each fanning out to per-module recipes. `just smoketest` (`nuke` → `start` → live pipeline verification → full test suite) turns the hand-run rebuild above into one command.
  - **Verify**: ran `just smoketest` for real (genuine `kind delete cluster`, not a simulation) — it caught two more real bugs immediately: (1) `verify-pipeline`'s Job-detection used `jsonpath '{.items[-1]...}'`, which crashes on an empty job list (the state right after `dagster job launch` returns, before the daemon has launched the actual k8s Job) — fixed with a before/after set-difference instead of list indexing; (2) `pkill -f` (SIGTERM) doesn't reliably kill `dagster dev` once its backing Postgres/cluster is already torn down — observed two processes surviving 10+ seconds past a "successful" `pkill`, fixed with a SIGTERM-then-poll-then-SIGKILL escalation in `orchestration::kill`, verified against both a synthetic SIGTERM-ignoring process and a normal responsive one (fast path still exits in <1s). Re-ran the full `just smoketest` end to end after both fixes: clean nuke, full rebuild, 8/8 `run_audit_log` rows `success`, full test suite green.
  - **New real test suites** (per the "write real tests now, not scaffolding" decision): `processing/raw_to_clean/tests/test_schema_validation.py` (codifies the Phase 6 ad hoc `validate_schema()` verification as committed pytest), `orchestration/dagster_data_platform/tests/test_dbt_assets.py` (`DataPlatformDbtTranslator.get_asset_key()`), `dbt/data_platform/models/staging/schema.yml` (real `not_null`/`unique`/`accepted_values` tests for both feeds — `accepted_values` sets read directly from `sales_assets.py`'s generator, not guessed).   - **Also surfaced, not a bug in the new tooling**: the kind container came back up on its own more than once shortly after a clean `docker stop`, with `RestartCount: 0` (rules out Docker's `on-failure` policy) — looks like a Docker Desktop for Mac VM-level quirk. `platform::start` already waits for real node readiness regardless, so this doesn't cause incorrect behavior, just means `docker stop`-as-pause isn't perfectly durable on this machine.

ON CONFLICT DO UPDATE ... RETURNING run_id`) then updating just that stage's column group, with `job_ended_timestamp`/`job_successful` rolling up on every stage completion.

- **Three real root causes found and fixed**: (1) the recurring `.pth` corruption bug — root-caused to `uv`'s default `link-mode=clone` (APFS `clonefile()`) setting the macOS `UF_HIDDEN` flag on installed files, which Python 3.13's `site.py` (a recent CPython security hardening, python/cpython#113659) silently skips; permanently fixed via `link-mode = "copy"` in root `pyproject.toml`. (2) A daemon schema-readiness race — `daemon_heartbeats` alone was an incomplete readiness proxy; `orchestration::start` now waits for the full 22-table `dagster_db` schema first. (3) **The real culprit behind most of this session's "flaky" pipeline failures**: `orchestration::kill`'s pattern only ever matched the top-level `dagster dev` wrapper, never its `dagster._daemon`/`dagster_webserver` children — three generations of orphaned child processes (PPID 1) had silently accumulated across this session's nuke-and-rebuild cycles, all fighting each fresh run's daemon over heartbeat ownership. Fixed by matching a path substring common to the whole process tree, catching orphans with no live wrapper to match against.
